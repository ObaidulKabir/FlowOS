# 29. Organizational team access

A tenant ("organization") often has several people who need to use FlowOS, and a shared API key
alone does not let each person sign in with their own identity. This chapter covers how an
organization gives its employees individual logins, who can manage those logins, and how that is
kept separate from the tenant's shared API keys.

## Two different kinds of credential

| Credential | Entity | Who holds it | Used for |
| --- | --- | --- | --- |
| Teammate login | `TenantUser` | One individual employee | Signing in to the dashboard as themselves, with their own password |
| Shared API key | `TenantApiKey` | The organization as a whole | Machine-to-machine calls: CRM, billing systems, CI pipelines, AI agents |

A `TenantApiKey`'s free-text **Application Name** field (visible on the "Scoped API Keys &
Runtime RBAC" tab) is only a label on that key — it is unrelated to the `TenantApplication`
entity used elsewhere in FlowOS, and unrelated to any person. Naming a key "DhopaExpress" does not
create anything a person can sign in as or that appears anywhere else in the dashboard.

Reserve shared API keys for machine-to-machine integrations. Give every employee who needs to use
the dashboard as themselves their own teammate login instead.

## Inviting a teammate

Only a tenant **Admin** (or a platform administrator) can invite a new teammate into a tenant.

1. `POST /api/tenants/{tenantId}/users` with `{ email, fullName, role }`. `role` is typically
   `"Admin"` or `"Employee"`. The response includes `inviteToken` — a 6-digit code — and the
   invite is also emailed to `email` from the platform's official sender address.
2. The invited person opens **Sign In → "Invited by a teammate? Accept your invite"**, enters
   their email and the code, and chooses their own password. Nobody else — including whoever
   invited them — ever sees or sets that password: `POST /api/auth/accept-invite` verifies the
   code and lets the teammate set it themselves.
3. They then sign in normally with `POST /api/auth/login` using their own email and password, and
   get their own JWT, scoped to the same tenant.

A teammate's login is a `TenantUser` row, the same entity used for the very first Admin created at
tenant registration (`POST /api/auth/register-tenant`) — an invite simply creates another one in
an already-existing tenant, rather than a new tenant.

`TenantUsers.Email` is unique across the whole platform, not just within one tenant: a person can
hold a teammate login in only one tenant at a time.

## Managing teammates

| Call | Who | Result |
| --- | --- | --- |
| `GET /api/tenants/{tenantId}/users` | Admin/SuperAdmin of that tenant, or a platform admin | Lists its teammates (email, full name, role, verification status, created/last-login) |
| `POST /api/tenants/{tenantId}/users` | Admin/SuperAdmin of that tenant, or a platform admin | Invites a new teammate (see above) |
| `DELETE /api/tenants/{tenantId}/users/{userId}` | Admin/SuperAdmin of that tenant, or a platform admin | Removes a teammate's login immediately |

A non-admin teammate (for example, role `"Employee"`) gets `403 Forbidden` from all three — they
can see their own profile via `GET /api/auth/me`, but cannot manage anyone else's access. A call
authenticated with a shared `TenantApiKey` rather than an individual login is also refused: a key
has no individual role to check against, so it is never treated as a privileged teammate here.

A tenant can never be left with no one able to manage it: removing the last remaining
Admin/SuperAdmin teammate is rejected (`400`) with a message asking you to promote someone else
first. This check looks only at each teammate's primary `Role` column; additional roles granted
through the separate Runtime RBAC system (the "Scoped API Keys & Runtime RBAC" tab) are not
considered.

In the dashboard, this all lives under **Platform Governance → Team**, next to (but separate from)
**Scoped API Keys & Runtime RBAC**.

## API key attribution and who can manage keys

Every `TenantApiKey` now records who generated it (`createdByUserId`), shown in the dashboard as
"Created by" next to each key. A key generated by a shared credential rather than an individual
login (or one generated before this feature existed) has no creator on record.

`GET /api/tenants/{tenantId}/keys`, `POST /api/tenants/{tenantId}/keys`, and
`DELETE /api/tenants/{tenantId}/keys/{keyId}` are now gated too, but differently from the teammate
endpoints above:

- An individual `TenantUser` login must hold the `Admin` or `SuperAdmin` role — previously *any*
  signed-in teammate of the tenant, regardless of role, could list, generate or revoke its keys.
- A **shared `TenantApiKey`** keeps the access it always had. Existing machine-to-machine
  automation that uses one key to mint or rotate other keys for the same tenant is unaffected by
  this change — only individual teammate logins are newly restricted.

In the dashboard, a non-admin teammate sees the API Keys tab with "Generate" and "Revoke"
disabled, with a note pointing them to an Admin on the Team tab.

## What this does not (yet) cover

- **Password reset / change.** There is still no self-service "forgot password" or "change my
  password" flow for an existing teammate. Removing and re-inviting them is the only way to issue
  a new one today.
- **Personal access tokens.** Only shared `TenantApiKey`s exist for API-level access; an
  individual teammate cannot yet mint their own scoped token tied to their personal identity.
- **Fine-grained invite roles.** `role` on invite is a free-text primary role, not validated
  against the Runtime RBAC role/capability system.

## MCP

This chapter has no MCP-facing behavior: teammate management is a dashboard/API-only concern, not
something an AI agent acting through the MCP server does on an organization's behalf.
